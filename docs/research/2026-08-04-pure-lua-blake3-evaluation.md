# Pure-Lua BLAKE3 evaluated against the Zig stdlib oracle

**Date:** 2026-08-04 · **Verdict:** the implementation is correct and fast
enough; **licensing is the only blocker.**

## Why this was tested

The deferred CSPRNG mode (PLAN.md → Future goals) wants a keyed DRBG. The
natural shape is `BLAKE3_keyed(seed).xof()` with seek. Zig gets BLAKE3 free
from `std.crypto.hash.Blake3`, but the LuaJIT reference implementation would
have needed either a runtime dependency on the official C `libblake3`
(nixpkgs `libblake3` 1.8.5, denting the README's "zero heavy deps" claim) or
a hand-written implementation (unacceptable reimplementation risk for
crypto). Peter proposed a third option:

> https://gist.github.com/Egor-Skriptunoff/50683d024cf6acdb89100564dc819b05

Same author as the well-regarded `pure_lua_SHA`. Tested rather than assumed.

## Method

Differential against **`std.crypto.hash.Blake3`**, using the **official
BLAKE3 test-vector methodology** rather than an ad-hoc corpus:

- input byte `i` is `i mod 251` (the reference repo's pattern)
- official key `"whats the Elvish word for friend"` (exactly 32 bytes)
- official KDF context `"BLAKE3 2019-12-27 16:29:52 test vectors context"`
- **41 input lengths** straddling every structural boundary — block (64),
  chunk (1024), and the 2/4/8/16-chunk subtree merges where BLAKE3's Merkle
  tree engages: 0,1..8, 63,64,65, 127,128,129, 255,256,257, 511,512,513,
  1023,1024,1025, 2048,2049, 3072,3073, 4096,4097, 5120,5121, 6144,6145,
  7168,7169, 8192,8193, 16384,16385, 31744
- **2 output sizes**: 32 (digest) and 131 (extended/XOF, the official
  vectors' length)
- **3 modes**: plain, keyed, derive_key

Harness: `scratchpad/b3/{zig_b3.zig,lua_b3.lua}` (see the session scratchpad;
reproduce by re-fetching the gist).

## Results

**246/246 vectors byte-identical** (41 lengths × 2 output sizes × 3 modes).

Sensitivity control — a differential that cannot fail proves nothing, so the
Lua input pattern was mutated (`i mod 251` → `(i+1) mod 251`) on one side
only: **240 of 246 lines diverged**, confirming the comparison bites. (The
6 survivors are the zero-length cases, where the input mutation is a no-op —
correct, not a gap.)

Independent cross-check against the **published** official vector for empty
input: `af1349b9f5f9a1a6a0404dea36dcc9499bcb25c9adc112b7cc9a93cae41f3262` —
matches both implementations.

### XOF with seek — already present

`digest_size_in_bytes = -1` returns a closure supporting
`f("seek", pos)` / `f(nbytes)`, i.e. unbounded keystream with random access.
This is exactly the DRBG primitive; nothing needs implementing.

Verified against a contiguous 4096-byte keyed stream generated by the Zig
stdlib: **6/6 out-of-order reads matched**, deliberately including
block-boundary-straddling and backwards seeks (`0,64`, `2048,128`, `63,2`,
`1000,100`, `4000,96`, `130,190`), so a "seek" that merely resumed
sequentially would have been caught.

### Performance (LuaJIT, this machine, ReleaseFast-equivalent)

| shape | throughput |
|---|---|
| bulk keyed hashing | **346 MB/s** CPU time (200 MB/s wall) |
| DRBG-shaped (64-byte keyed draws) | **~308,000 draws/s** |

The benchmark asserts the digest still equals a precomputed expectation
inside the timed loop, so a hash being optimized away or short-circuited
cannot masquerade as speed. CPU time is the headline figure per the fleet
convention for single-threaded compute kernels; wall differs because the
machine was busy.

For scale: optimized C BLAKE3 with SIMD runs several GB/s, so this is
roughly an order of magnitude off the C library — and still far faster than
this use case needs (a fuzz loop drawing 64 random bytes per iteration would
spend ~3µs/draw).

## Blocker: no license

The gist carries **no license header, and no license field in its gist
metadata** (checked via the GitHub API: description "BLAKE3 for LuaJIT",
files `blake3_for_luajit.lua` / `blake3_for_luajit.test.lua`, no SPDX or
copyright line anywhere in the source). Absent an explicit grant, default
copyright applies and vendoring it into an MIT-licensed repository is not
something to do quietly.

Resolution paths, in order of preference:

1. **Ask the author** to add a license (he licensed `pure_lua_SHA` MIT, so
   this is likely a simple oversight and a one-line answer).
2. Depend on nixpkgs `libblake3` via FFI for the LuaJIT side (correct and
   official, at the cost of a runtime dep — which is *also* what the
   `getrandom` FFI work introduces anyway, so the marginal cost is smaller
   than it first appears).
3. Use **ChaCha20** instead of BLAKE3 for the DRBG: ~30 lines of pure Lua
   (quarter-round + 20 rounds over 16 u32 words), RFC 8439 supplies official
   test vectors as an external oracle, and Zig has `ChaCha20IETF` in std.
   Strictly simpler to get right than BLAKE3, and equally standard as a
   keyed stream. Loses BLAKE3's seek-by-construction, but counter mode
   (`key, nonce=counter`) recovers O(1) random access anyway.

**Note on option 3, which applies to BLAKE3 too:** XOF seek is a
convenience, not a requirement. `blake3(counter_bytes, key, 64)` — plain
keyed hashing of a counter — already gives O(1) random access to draw *N*
using only the API verified above. That is the shape the DRBG benchmark
measured.

## Recommendation

Correctness and performance are settled: this implementation is bit-exact
against the Zig stdlib across the official vector methodology, including
keyed and derive_key modes and seekable XOF, at ~346 MB/s. Do not adopt it
into the repo until licensing is resolved. Pursue (1); fall back to (3),
which is independently attractive for being small enough to audit line by
line.
